# 01 — Project manual: deviations, installation and principles

This document **does not reproduce** the project guide (`GUIA_PROYECTO_FINAL_ECBD.md`, a course document that is not part of this repository). It only records where the current implementation departs from the guide, the installation note and the team principles behind it. For everything else, the guide remains the source of truth.

## 1. Deviations from the guide

| # | Topic | What the guide says or suggests | What the project does | Reason |
| :-- | :-- | :-- | :-- | :-- |
| 1 | Automated tests | Tests and CI | No pytest, no tests folder and no CI. Verification is the pipeline's `validate` stage, the `data_quality_report.csv` log, the ad hoc queries documented in `docs/03`, Git checks and `ruff check .` | Team decision: project scope and deadline |
| 2 | Data download | Automatic download with the Kaggle API (`scripts/download_data.py`, `kaggle.json`) | No `download_data.py`, no `kaggle` package and no `kaggle.json`. The 9 Olist CSV files are obtained by extracting the versioned original archive `data/raw/olist/IT91_CSV_Olist_Data_Original_ECBD.zip` into `data/raw/olist/` (see [`docs/08-setup-and-run.md`](08-setup-and-run.md)) | Avoids credentials on the team's PCs and one more dependency |
| 3 | `.editorconfig` | Included in the structure | Not included | Formatting is set by `ruff.toml` (Python) and `.gitattributes` (LF line endings in CSV files) |
| 4 | `config/settings.example.toml` | Configuration template in `config/` | Does not exist. Configuration lives in code, in `packages/etl/src/ecbd_etl/config.py` (period, seed 42, paths, Brazil bounding box, UF → region map, catalogs); the `config/` folder was removed by user decision (2026-11-13) | A single place for configuration and no `tomllib`/`tomli` (Python 3.10 does not ship `tomllib`) |
| 5 | Linter configuration | — | `ruff.toml` at the root (rules E, F, I and PTH; the latter forbids `os.path`) instead of a section in a `pyproject.toml` | This way it also applies to `scripts/`; a root `pyproject.toml` would suggest a second package |
| 6 | ETL modules | Eight modules: `config`, `extract`, `clean`, `enrich`, `model`, `quality`, `load`, `pipeline` | The list is kept: the 14 rules of the `validate` stage and the exceptions live in `quality.py`; there is no `validate.py` | No files added outside the guide's structure |
| 7 | Quality log | Record of the rules applied | **4-column** log (`stage, rule, rows_affected, action`) with a closed list of 45 rules, including those with 0 rows | Full traceability, comparable across runs |
| 8 | Dependencies | Base list | `requirements.txt` with the full environment of Step 1 of the assignment: `pandas>=2.2`, `numpy>=1.26`, `matplotlib`, `seaborn`, `plotly`, `jupyter`, `ruff`, `-e packages/etl` and `-e packages/viz-kit` (the local `ecbd_viz` package used by the notebook) | A single install command for the ETL, the notebook and the linter |
| 9 | Customer, seller and product dimensions (section 6.6) | Full catalogs | `dim_customer`, `dim_seller` and `dim_product` contain **only the keys used** by the fact table | No orphan rows in the Power BI model |
| 10 | Grain of `dim_customer` | — | One row per `customer_id` (unique per order in Olist); `customer_unique_id` is kept as an attribute to count distinct customers and measure repeat purchases | Consistency by construction between `dim_customer`, `distance_km` and `analytics_flat` |
| 11 | Fact table foreign keys | Schema section 6.6 | **9 foreign keys**: `purchase_date_key`, `delivered_date_key`, `estimated_date_key`, `customer_key`, `customer_state_key`, `seller_key`, `product_key`, `payment_type_key`, `order_status_key` (see `docs/04`) | Three date roles and the customer's state with its population |
| 12 | Delivery before purchase (section 6.2) | Exclude and log | The order is **kept** (it stays in the GMV), flagged with `delivery_data_missing = 1` and its delivery metrics are set to null; rule `delivered_before_purchase` (`flagged`) | Real sales are not lost because of a date error |
| 13 | Added columns | — | `purchase_hour` (purchase hour), `delay_band_order` (order 1–5 of `delay_band`), `delivery_data_missing` (single invalid-delivery flag) and `dims_imputed` (weight or dimensions imputed) | Band order in charts, Late Rate denominator and imputation traceability |
| 14 | Commercial calendar and category map | Reference inputs | `commercial_calendar.csv` (Black Friday, Christmas, Mother's Day and World Cup 2018) and `category_macro_map.csv` (74 categories → 8 macro categories in English) are **authored by the team** | The guide does not provide those files |
| 15 | Large files (Git LFS) | Git LFS for `.pbix` and data | No Git LFS. `*.pbix` is marked as binary in `.gitattributes` (it must be under 100 MB). `analytics_flat` uses neither LFS nor Parquet: since the plain CSV was 77.6 MB (> 50 MB), it is written as `analytics_flat.csv.gz` (gzip with `mtime` 0, deterministic) and is still one of the 10 files in `data/processed/`. The original Olist archive (42.6 MiB, below 50 MiB) is also versioned without LFS (see row 16). The notebook therefore reads `analytics_flat.csv.gz` instead of the guide's `analytics_flat.csv` | No extra tools needed to clone; pandas reads the gzip directly |
| 16 | Olist source data | The Olist CSV files stay in `.gitignore` and are downloaded | The original Olist archive `data/raw/olist/IT91_CSV_Olist_Data_Original_ECBD.zip` is versioned unmodified; the rest of `data/raw/olist/` (the extracted CSV files) stays ignored | CC BY-NC-SA 4.0 allows non-commercial redistribution with attribution under the same license; the archive (42.6 MiB) is below GitHub's 50 MiB warning threshold; the extracted CSV files remain unversioned |
| 17 | README | README template of the guide (section 13), with requirements, installation, running and structure in the README itself | A shorter root README (overview, quick start, Documentation index, credits, licenses and team) that points to [`docs/08-setup-and-run.md`](08-setup-and-run.md) for setup and running and to [`docs/09-repository-structure.md`](09-repository-structure.md) for the structure | User decision (2026-11-13): a short README with an index is easier to review, and the detail stays versioned in `docs/` |

## 3. Team principles applied

The principles come from the project constitution, an internal team document that is not versioned in this repository. This table summarizes the ones the ETL pipeline applies.

| Principle | How it is met here |
| :-- | :-- |
| Section 1: Open public data | Only public data (Olist, IBGE); the original Olist archive is versioned unmodified and the extracted CSV files are not versioned (see [`docs/08-setup-and-run.md`](08-setup-and-run.md)); no credentials: `.env` and `kaggle.json` are ignored and `.env.example` only holds a placeholder |
| Section 2: Reproducible pipeline | `python scripts/run_pipeline.py` runs end to end with no manual steps once the 9 CSV files are extracted from the archive (see [`docs/08-setup-and-run.md`](08-setup-and-run.md)) (`extract → clean → enrich → model → validate → load`), with seed 42 and an explicit row order; `validate` checks unique keys and the absence of orphans, and the log is written to `data_quality_report.csv` |
| Section 3: Explicit lineage | Every column has its source and formula in `docs/02-data-dictionary.md`, and the relationships, cardinalities and keys are in `docs/04-star-schema.md` |
| Section 5: Living documentation | Documentation is versioned with the code in `docs/` and is updated in the same change that modifies the ETL |
